# 캐스퍼 검색 함수와 rag.py 수정본

## 현재 상태

수정 파일을 만든 상태입니다. 실제 DB에는 SQL을 실행하지 않았습니다.
팀 프로젝트 원본 rag.py의 쓰기 권한이 허용되지 않아 원본은 수정하지 않았습니다.
앱 실행이나 실제 DB 검색 비교도 아직 수행하지 않았습니다.

## 적용 순서

1. DBeaver에서 **팀 DB** 연결을 선택합니다.
2. `01_match_manual_chunks_hybrid.sql`을 열어 전체 실행합니다.
3. 기존 `C:\mle-02-p1-team1\src\car_search_rag\casper_manual\src\rag.py`를 백업하고, 이 폴더의 `rag.py`로 덮어씁니다.
4. 배포 앱이라면 해당 파일을 커밋·push하고 배포 반영 후 앱을 다시 실행합니다.
5. `차량 제원이 궁금해`, `캐스퍼 크로스의 축거를 알려줘`와 기존 평가 질문의 검색 근거·답변을 비교합니다.

DB 함수를 먼저 적용해야 합니다. 새 함수가 없으면 수정한 rag.py는 오류를 반환하며, 옛 검색으로 자동 전환하지 않습니다.
개인 DB에서 먼저 적용하려면 실제 테이블명을 확인하세요. 개인 DB가 `manual_chunks`/`manual_embeddings`를 사용한다면 SQL에 있는 `public.casper_manual_chunks`와 `public.casper_manual_embeddings`를 해당 이름으로 바꿔 실행합니다.

## 무엇이 달라졌나요?

기존: 질문 → E5 벡터 → 벡터 유사도 상위 5개 → 이미지 연결 조회 → 답변 생성.

변경: 질문 → E5 벡터와 검색 단어 → 벡터 후보 + 제목·본문 키워드 후보 → 순위 결합 → 상위 5개 → 이미지 연결 조회 → 답변 생성.

### DB 함수

- 기존 함수를 남겨두고 새 `match_manual_chunks_hybrid` 함수를 추가합니다.
- 모델·버전이 일치하는 임베딩을 가진 청크만 두 검색의 대상이 됩니다.
- 벡터 검색과 키워드 검색에서 기본 50개씩 후보를 모으고, 같은 청크는 한 번만 반환합니다.
- 키워드는 대소문자를 구분하지 않는 문자열 포함 검색입니다. 한국어 형태소 분석이나 PostgreSQL 전문 검색(FTS)을 사용하지 않습니다.
- 제목·장·절·소제목의 일치는 본문 일치보다 가중치를 높입니다(4 대 1).
- 많은 청크에 등장하는 단어보다 적은 청크에 등장하는 단어에 더 높은 가중치를 줍니다. 본문에 같은 단어가 반복되어도 반복 횟수로 가중치를 더하지 않습니다.
- 질문 안에 완전한 제목이 들어 있으면 추가 점수를 줍니다. 공백을 제외한 제목이 4자 이상일 때 적용합니다.
- 두 후보 목록의 순위를 RRF 방식으로 결합합니다. 초기 설정은 벡터 가중치 1, 키워드 가중치 2, 순위 상수 20입니다. 최적값으로 검증된 설정은 아닙니다.
- 키워드가 없거나 일치하지 않으면 벡터 후보만으로 순위를 정합니다.
- 기존 데이터, 임베딩, 이미지 테이블, 외래 키를 변경하지 않습니다. 추가 확장 설치도 필요하지 않습니다.

### rag.py

- 원래 질문은 그대로 `query:` 접두사를 붙여 임베딩합니다.
- 질문에서 검색 단어를 추출해 새 함수에 보냅니다.
- `궁금해`, `알려줘` 같은 표현과 차종 전체에서 공통적인 단어는 제외하고, 제한적인 조사 제거를 적용합니다.
- 예: `캐스퍼 크로스의 축거를 알려줘` → 검색 단어 `크로스`, `축거`.
- 질문을 LLM으로 다시 작성하거나 동의어로 확장하지 않습니다.
- 검색 결과의 이미지 연결 조회, 실제 이미지의 답변 모델 전달, 답변 출처 번호는 기존 코드를 유지합니다.
- 빈 질문, top_k 범위, 질문 길이를 확인합니다. 최대 질문 길이는 2,000자입니다.

## 결과 필드 읽는 법

| 필드 | 의미 |
|---|---|
| similarity | 기존과 같은 코사인 유사도. 정답 확률이 아닙니다. |
| lexical_score | 제목·본문의 키워드 일치 점수. 유사도와 척도가 다릅니다. |
| hybrid_score | 두 후보 목록의 순위를 결합한 최종 정렬 점수 |
| vector_rank | 벡터 후보 목록 내 순위. 후보 밖이면 null |
| keyword_rank | 키워드 후보 목록 내 순위. 후보 밖이면 null |
| matched_terms | 해당 청크의 제목이나 본문에서 발견한 검색 단어 |

최종 결과는 hybrid_score로 정렬합니다. UI에서 similarity로 다시 정렬하면 결합 검색의 순서가 사라집니다.
현재 UI가 새 진단 필드를 자동으로 보여주는 것은 아닙니다. rag.py가 반환하는 sources 안에서 확인할 수 있습니다.

## 한계와 확인할 부분

- 이번 수정은 검색 경로의 개선입니다. PDF 표 전처리, 청킹, 임베딩은 다시 만들지 않았습니다.
- 원문에서 축거 등의 글자가 누락되었다면 문자열 검색으로 복구할 수 없습니다.
- 표의 차종과 수치 관계가 깨진 청크는 검색되더라도 답변 해석이 틀릴 수 있습니다. 답변과 원본 표를 비교해야 합니다.
- 단순 조사 제거와 문자열 포함 검색에는 오탐·누락이 생길 수 있습니다. 완전한 형태소 분석이나 동의어 검색이 아닙니다.
- 키워드가 있는 청크라고 무조건 질문의 정답을 포함하는 것은 아닙니다.
- 이번 함수는 현재 약 1,874개 규모에서 적용할 초기 구현으로, 대상 청크를 스캔합니다. 데이터가 크게 늘어나면 인덱스와 검색 방식, 실행 계획을 검토해야 합니다.
- 성능 향상과 기존 질문의 품질 유지는 실제 실행 결과로 확인해야 합니다. 이번 수정에 대해 검색 성공률이 높아졌다고 아직 주장할 수 없습니다.

## 되돌리기

원본 백업 `rag_before.py`를 원래 위치의 `rag.py`로 복원합니다. 기존 `match_manual_chunks`가 남아 있으므로 옛 검색으로 돌아갑니다.
새 함수는 앱에서 호출하지 않으면 사용되지 않습니다.
